# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`legal-agent` is a Vietnamese-legal-domain RAG chatbot. Long-term architecture is hybrid retrieval — OpenSearch (BM25) + ChromaDB (semantic) + Neo4j (knowledge graph), fused via RRF, orchestrated by a tool-calling LLM agent, with Postgres as the source of truth. **Most of that is still not built.** Read `README.md` before assuming any retrieval/agent component exists — it documents the target architecture and explicitly marks what's proposal-only vs. done.

The server (`server/`) is deliberately split into **two independent workflows**, not meant to reconcile with each other:

- **`server/src/download/` + `server/src/catalog/` + `server/src/utils/`** — scrapes vanban.chinhphu.vn into a flat file corpus (`laws/`), tracked by a JSON manifest, no database. Built for offline dataset-building (text processing, ML, ad-hoc analysis), scoped to all 14 Điều 4 tiers. Formerly one umbrella `server/src/law/` module; flattened into three top-level modules (see "Architecture" below) since nothing else in this repo groups by that boundary.
- **`server/src/crawl/` + `server/src/persistence/` + `server/src/retrieve/` + `server/src/sync/` + `server/src/job-queue/` + `server/src/opensearch/`** — scrapes [vbpl.vn](https://vbpl.vn/) ("Cơ sở dữ liệu quốc gia về pháp luật", Bộ Tư pháp) and writes into Postgres. This is the actual ingestion path for the production RAG/chatbot system, scoped to **Trung ương only** (tiers 1–9 — central-issued documents have nationwide effect; local tiers 10–14 don't and are out of scope), **minus tier 4 (Lệnh, Quyết định của Chủ tịch nước) — deliberately excluded, not just not-yet-done.** Most tier-4 instruments are procedural (công bố luật, bổ nhiệm chức vụ, khen thưởng, …) rather than substantive legal content, so they don't contribute to the RAG corpus the way the other tiers do. vbpl.vn was chosen over vanban.chinhphu.vn as the **primary** source for this workflow because it exposes a validity-status field, clean full text, and a curated relationship graph that vanban.chinhphu.vn structurally lacks — at the cost of needing a headless browser (Playwright) instead of a plain HTTP client, since it's a Next.js SPA. Formerly one umbrella `server/src/law-index/` module; fully dismantled — every submodule is now top-level, and the umbrella's own controller/service/config merged into `crawl/` (see "Architecture" below) rather than surviving as a separate piece. `crawl/` also now indexes vanban.chinhphu.vn as a **supplementary** source (formerly a separate `server/src/crawl-chinhphu/` module, now fully dismantled the same way `law-index/` was — see "Architecture" below) — precisely because it lacks that same relationship graph, a document synced from vanban.chinhphu.vn gets **zero `document_reference` rows, permanently, in either direction**, not just until some feature ships; see the `crawl/` Architecture bullet for the rest of that gap (no validity status, metadata-only until a text-extraction tool exists).

Current build sequence (see README "Sequencing"): 3 search engines provisioned (done) → Postgres as source of truth (`document`/`issuing_body`/`document_reference`/`document_node` rows now being written by `crawl/`, including the Điều/Khoản/Điểm/Phụ lục hierarchy) → CDC + sync-state + reconciliation (not started) → OpenSearch/ChromaDB/Neo4j projectors (not started) → agent/orchestration layer (not started).

## Commands

All commands run from `server/`:

```bash
npm run start:dev       # NestJS dev server with watch mode
npm run build            # nest build
npm run lint              # eslint --fix on src/apps/libs/test
npm run format             # prettier --write on src/ and test/
npm test                    # jest unit tests (run from server/, rootDir is src/)
npm test -- <pattern>        # run a single spec, e.g. npm test -- law-tier-classifier
npm run test:cov              # jest with coverage
npm run test:e2e               # e2e tests (test/jest-e2e.json)
```

Infra (Postgres/OpenSearch/ChromaDB/Neo4j), from the repo root:

```bash
cp .env.example .env      # then set strong passwords
docker compose up -d
docker compose ps          # all services should be `healthy` within ~60s
```

Server config: copy `server/.env.example` to `server/.env` (separate from the root `.env` used by docker-compose). `server/src/config/env.validation.ts` is the authoritative list of required env vars — Postgres/OpenSearch/Neo4j/ChromaDB connection info, `PORT`, `LAWS_DOWNLOAD_DIR`. The app fails fast on startup if any required var is missing.

Swagger/OpenAPI UI is served at `/api` once the server is running.

**Find the server port from this worktree's `server/.env`, never by probing ports or hunting for a process.** This repo is checked out as several git worktrees at once (`git worktree list` — e.g. `.kilo/worktrees/secondary-workdesk`, `.kilo/worktrees/test-workdesk`), each on its own branch, each with its own `server/.env` and its own `PORT`. A server answering on some port is therefore *not* evidence it belongs to the worktree you're working in — it is usually a sibling worktree running different code against the same Postgres. Read `PORT` from the `server/.env` of the directory you are actually in (the primary worktree is `PORT=3000`) and use only that one. Never start a server on a port you picked yourself: that collides with whichever worktree owns it. If a change doesn't appear to take effect, the cause is almost always a failing `npm run build` — `nest start --watch` keeps serving the last good compile silently — so run `npm run build` before concluding anything about the running server.

## Architecture

### `server/src/download/`, `server/src/catalog/`, `server/src/utils/` — the fully-implemented workflow-A modules

**Formerly one umbrella `server/src/law/` module (`law.module.ts`, now deleted) — flattened into three top-level modules, one at a time (see git history/branch `migration/module-reorganize`).** Each is registered directly in `AppModule`, and their endpoints dropped the `laws`/`law` prefix (`download/`'s routes are `/downloads`, `catalog/`'s are `/catalog`, both not `/laws/...`). This flattening is now complete for workflow A, and the same push is now also **fully complete on workflow B's side** — `server/src/law-index/` no longer exists as a directory at all. `crawl/`, `retrieve/`, `sync/`, `job-queue/`, and `opensearch/` are now top-level modules, and `persistence/` is a top-level plain relocation (no module wrapper — it isn't a business submodule the way the others are, just Drizzle schema + repositories + the DB connection factory; `DocumentRepository`/`DocumentNodeRepository` stay exactly where they were already registered as flat providers on each consuming module, not consolidated into one). The umbrella's own `law-index.controller.ts`/`.service.ts`/`.module.ts`/`.config.ts` didn't get a top-level home of their own — they were merged straight into `crawl/` (as `CrawlController`/`CrawlService`/`crawlConfig`) since `crawl/` already owned every DTO those endpoints used and the umbrella's config had no real consumers outside `crawl/`'s own client services. Not every moved submodule ended up registered directly in `AppModule`, though: `job-queue/` has no controller of its own, so it's wired in purely through its mutual `forwardRef()` relationship with `CrawlModule` — see that bullet below.

- **`download/`** — fetches documents from vanban.chinhphu.vn (the *only* source this module ever hits) via `VanBanChinhPhuClientService` (HTTP + cheerio HTML parsing) and `vanban-chinh-phu.parser.ts`. `LawDownloadService` orchestrates single-URL, batch (up to 100), and filtered-search downloads. `law-tier-classifier.ts` maps each document's type + issuing body to one of the 14 statutory tiers (Điều 4, Luật 64/2025/QH15); unrecognized types return an error rather than guessing, unless the caller passes `subdirOverride`.
- **`catalog/`** — read-only browsing/serving of what's already downloaded (`law-catalog.service.ts` + controller). Never touches the network. Fuzzy title search via `fuse.js` with diacritics folding; a document with attachments streams back as a zip, single-file documents stream as-is.
- **`utils/`** — plumbing shared across top-level modules that need it (currently `download/` and `catalog/` — `law-index/` deliberately doesn't): `LawManifestService` (the `laws/manifest.json` / `laws/download-log.csv` read-write layer, registered as the one shared provider in `LawUtilsModule`), plus pure non-DI helpers imported directly where needed — `document-matcher.ts` (title/citation matching), `tier-definitions.ts`, `text-normalize.util.ts`. (`filename.util.ts` lives in `download/` instead, since nothing else uses it.)

Every Bộ luật/luật document — base laws, superseded versions, and amendment laws alike — lands in one flat `02-luat-nghi-quyet-quoc-hoi/luat-bo-luat/` folder, regardless of validity status: this dataset is a text corpus for retrieval, not a "current law" database, so the classifier doesn't need to decide what's still in force. (An earlier version routed by title-based supersession detection into separate `luat/`/`luat-het-hieu-luc/`/`luat-sua-doi-bo-sung/` folders; that logic was removed once the `laws/` dataset stopped needing to double as a validity signal.) See `server/README.md` for the full endpoint list.

### `server/src/crawl/`, `server/src/persistence/`, `server/src/retrieve/`, `server/src/sync/`, `server/src/job-queue/`, `server/src/opensearch/` — the Postgres ingestion modules (formerly one `law-index/` umbrella, now fully dismantled)

Same layered pattern as `download/` above (client / parser / service / module), plus a `persistence/` layer:

- **`crawl/`** — two things merged into one module. (1) The vbpl.vn client layer: `VbplClientService` drives a real headless browser (Playwright) since vbpl.vn is a Next.js SPA whose document data renders client-side (confirmed by direct investigation — not present in raw server-rendered HTML, and not worth reverse-engineering the site's internal Next.js Server Action/RSC protocol). For each document it does 3 throttled page loads (default tab = full text, `?tabs=thuoc-tinh` = attributes, `?tabs=luoc-do` = relations) and returns *raw, uninterpreted* DOM extractions. `VbplSitemapService` does document discovery via plain HTTP against `sitemap.xml` (no browser needed — static XML), split into a Trung ương block (this module only ever follows this one) and a Địa phương block. `vbpl.parser.ts` and `document-node.parser.ts` are the pure, DI-free layer (the former mirrors `vanban-chinh-phu.parser.ts`) that turns the client's raw extractions into typed domain objects — including `RELATION_LABEL_MAP`, which maps vbpl.vn's 26 relation-card headings (13 concepts × inbound/outbound phrasing) to the schema's `reference_type`/`change_type` values. (2) The scrape-and-sync orchestration layer: `CrawlService`/`CrawlController` (formerly `LawIndexService`/`LawIndexController` under the now-dismantled `law-index/` umbrella — merged here since `crawl/` already owned every DTO the controller used, and the umbrella's config had no real consumers outside `VbplClientService`/`VbplSitemapService` to begin with). `CrawlController`'s routes dropped the `/laws/index` prefix entirely — `POST`/`PUT /crawl/url`, `POST`/`PUT /crawl/batch`, `POST /crawl/all`, `GET`/`POST /crawl/search`, `GET /jobs/:jobId`, `POST /jobs/:jobId/cancel` (job endpoints are path siblings of `crawl/*`, not nested under it — the controller itself has no route prefix, each method's own `@Post('crawl/url')`/`@Get('jobs/:jobId')` etc. is the full literal path). Swagger tag is now `crawl`, not the old shared `law-index` tag (which no longer exists as a tag at all). `crawlConfig` (`crawl.config.ts`, formerly `lawIndexConfig`/`law-index.config.ts` — `registerAs` namespace renamed `lawIndex`→`crawl`, but the underlying env var names, e.g. `VBPL_BASE_URL`/`LAW_INDEX_MAX_TIER`, were deliberately left unchanged since renaming those would be a real `.env`-compatibility break, not just a code-structure one) is injected by `VbplClientService`/`VbplSitemapService`, the only two real consumers.

  vanban.chinhphu.vn as a supplementary source was formerly a separate `server/src/crawl-chinhphu/` module (its own controller/service/module, mirroring `crawl/`'s original shape); fully dismantled into `crawl/` the same way the `law-index/` umbrella was — same rationale: nothing else in this repo groups by that boundary, and `crawl/` already owned `CrawlService`, the one thing `FallbackSearchService` (below) needs a real instance of. Reuses `download/`'s `VanBanChinhPhuClientService` (plain HTTP + cheerio — vanban.chinhphu.vn is server-rendered, no browser needed for this source) and `vanban-chinh-phu.parser.ts`'s `parseDocumentDetailPage`/`parseSearchPage` for the HTTP/HTML layer, provided here as `crawl/`'s own instance (same pattern as `DocumentRepository`/`DocumentNodeRepository` being re-provided per top-level module, not exported/shared from `download/`'s own module). `parseSearchPage` also now exposes the "Cơ quan ban hành" (`drdDocOrg`) `<select>`'s own `{value, label}` option list (`ParsedSearchPage.orgOptions`) — confirmed live its option `value` is an opaque internal id unrelated to the label text (e.g. `<option value="1">Quốc hội</option>`), unlike "Năm ban hành" (`drdDocYear`), whose option value equals its label, needing no lookup.
  - `chinhphu-crawl.service.ts`'s `ChinhPhuCrawlService` (`POST /crawl/chinhphu/url`) parses a vanban.chinhphu.vn detail page into `ParsedChinhPhuDocument` (`chinhphu-document.interface.ts`) and upserts it via `persistence/chinhphu-document.repository.ts`'s `ChinhPhuDocumentRepository` — deliberately separate from `DocumentRepository`, whose citation-collision/consolidation/relation logic is written specifically against vbpl.vn's data shape and known failure modes (e.g. its "Không số" citation reuse) that don't apply here. `ChinhPhuDocumentRepository` never overwrites a document already indexed under the same citation by another source (skips with a `skippedReason` instead) and reuses `DocumentRepository.resolveOrCreateIssuingBody` rather than duplicating it (`issuing_body` is a shared table with no source-specific meaning).
  - **Known, permanent limitation** (not a TODO): a vanban.chinhphu.vn-sourced document gets **zero `document_reference` rows, ever, in either direction** — vbpl.vn's "Lược đồ" tab gives `crawl.service.ts`'s `upsertRelations`/`extractTextReferences` a curated relationship graph plus full text to mine inline citations from; vanban.chinhphu.vn has neither. It also has no `Tình trạng hiệu lực` field (so `document.status` stays `null` for these rows) and no server-rendered full text at all — only downloadable PDF/DOC/RTF attachments (`ParsedChinhPhuDocument.attachmentFileUrls`) — so every document synced today is persisted with `indexScope: 'metadata_only'` and no `document_node` tree. `document-text-extractor.ts`'s `DOCUMENT_TEXT_EXTRACTOR` port is the extension point for a future OCR/VLM document-processing tool (still under evaluation in `sandbox/extract-tool-resilience` and `sandbox/text-extract-evaluation`, outside this worktree) — swap `NullDocumentTextExtractor` for a real implementation once one exists; `document-node.parser.ts`'s `parseDocumentBody` and `document-node.repository.ts`'s `syncNodes` (narrowed to a minimal `DocumentTextSource { fullText }` contract rather than vbpl.vn's own `ParsedVbplDocument`, specifically so this source can feed it too) are already wired to pick that up the moment `fullText` stops being `null` — but the relations gap above stays permanent regardless.
  - `chinhphu-search.service.ts`'s `ChinhPhuSearchService` is a read-only search against vanban.chinhphu.vn's own "TÌM KIẾM VĂN BẢN" form, scoped to the 3 filter dimensions `fallback-search.service.ts`'s `FallbackSearchService` needs (keyword/org/year) and never downloading files — deliberately duplicates (rather than shares) `download/law-download.service.ts`'s `fetchSearchResults` pagination logic, per this project's "two independent workflows, not meant to reconcile" stance. `resolveOrgId` matches an exact "Cơ quan ban hành" name against the live `orgOptions` list; confirmed live at least one body is listed under two different ids (an administrative reorg over time) — a 0-or-2+-match name searches without an org constraint (logged, not thrown) rather than guessing which id is right.
  - `fallback-search.service.ts`'s `FallbackSearchService` is what `GET /crawl/search` actually calls now (previously `CrawlService.searchDocuments` directly) — searches vbpl.vn first with the endpoint's full existing filter set (`VbplSearchFilters`, unchanged), and only falls back to vanban.chinhphu.vn (using the 3-dimension subset above, deriving a single year from `issuedFrom`/`issuedTo` and taking just the first `issuingBodies` entry) when vbpl.vn returns zero matches — or throws `BadRequestException` because `issuingBody` isn't one of vbpl.vn's own recognized sidebar checkbox labels (`VbplClientService.applySidebarCheckboxes`), functionally the same "no path via search" signal. A real vbpl.vn outage (`BadGatewayException`) or an in-progress crawl holding the browser lock (`ConflictException`) is **not** treated as "no results" and propagates instead of silently falling back. The response is now a `{ source, result }` envelope (`FallbackSearchResponseDto`) rather than always vbpl.vn's own response shape — `CrawlService.searchAndSyncDocuments` (the `POST /crawl/search` auto-sync endpoint) was deliberately left untouched, still vbpl.vn-only, since folding the fallback into an auto-sync path is a materially bigger decision than a read-only search endpoint.
- **`persistence/`** (a top-level plain relocation, not under `law-index/` anymore — no module wrapper, just Drizzle schema + repositories + the DB connection factory) — Drizzle ORM schema (`schema/*.schema.ts`) + `db.module.ts` (reuses the existing `postgresConfig` namespace — this module is the first thing in the repo to actually open a Postgres connection) + `document.repository.ts` (upsert logic: resolve-or-create `issuing_body`, upsert `document` gated on a `content_version` hash so unchanged re-scrapes are cheap no-ops, upsert `document_reference` with forward-reference healing for relations pointing at not-yet-scraped documents) + `document-node.repository.ts` (`syncNodes()`: full delete-and-reinsert of a document's `document_node` tree, gated the same way — skipped when content is unchanged and nodes already exist). `migrations/` + `drizzle.config.ts` (server root) moved with it — `schema`/`out` in `drizzle.config.ts` now point at `./src/persistence/...`.
  - **Known gap, found while moving this: `migrations/meta/` has no snapshot JSON for migrations 0006 or 0007** (`0006_quick_shockwave.sql`, `0007_add_missing_fk_indexes.sql` — confirmed never committed, not something this move deleted). `drizzle-kit`'s last tracked state is `0005_snapshot.json`, so `npm run db:generate` doesn't know 0007's indexes were already applied and will offer to regenerate them as a new migration (`CREATE INDEX` on names that already exist in the live DB — it would fail if actually run). Hit this immediately after moving `persistence/`; deleted the spurious generated migration + snapshot and restored `_journal.json`, don't apply it. Not fixed — real but pre-existing and out of scope for the module-flattening work itself.
- **`retrieve/`** (`RetrieveModule` registered directly in `AppModule` — nothing else in the DI graph injects `RetrieveService`, it only ever needed importing for controller registration, which `AppModule` now does directly) — read/search/delete over already-synced Postgres rows, the read counterpart to `crawl/`'s write path. Routes dropped the `/laws/index` prefix (`GET /retrieve`, `GET /retrieve/nodes`, `GET /retrieve/references`, `GET /retrieve/issuing-bodies`, `GET /retrieve/:id`, `DELETE /retrieve/:id`, `DELETE /retrieve`), swagger tag is `retrieve`. Depends on the shared `crawl/dto/search-documents-response.dto.ts` (moved there along with the rest of the dismantled umbrella's DTOs — also used by `crawl/`'s own `search-sync-documents-response.dto.ts` and `crawl.controller.ts` itself, genuinely cross-cutting between the two modules).
- **`sync/`** (same treatment as `retrieve/`: `SyncModule` registered directly in `AppModule`, nothing else injects `SyncService`) — heals `document_reference` rows left dangling when a citation's target document hadn't been scraped yet at reference-extraction time; operates entirely on existing Postgres data, never touches vbpl.vn. Routes dropped the `/laws/index` prefix (`PATCH /sync/refs/document`, `PATCH /sync/refs/all`, `PATCH /sync/refs/batch`, `POST /sync/refs/extract`, `GET /sync/refs/dangling`), swagger tag is `sync`. No test files exist for this submodule at all (`sync.controller.spec.ts`/`sync.service.spec.ts`/`sync.module.spec.ts` are all absent) — a pre-existing gap, not introduced by this move.
- **`job-queue/`** — *not* registered directly in `AppModule` the way `retrieve/`/`sync/`/`opensearch/` are, since it has no controller of its own. BullMQ wrapper for the async crawl endpoints (`POST /crawl/all`, `POST`/`PUT /crawl/batch`, `POST /crawl/search`, all on `CrawlController`; see `docs/plan/scraper-resilience-plan.md`). `JobQueueService` submits/polls/cancels jobs against a Redis-backed `Queue`; `JobWorkerService` owns the single BullMQ `Worker` (concurrency 1 — `VbplClientService`'s browser/page lock would serialize concurrent jobs anyway) and dispatches each job to the matching `CrawlService` batch method. This is the one submodule with a **genuine two-way dependency** on `CrawlModule` (formerly `LawIndexModule`, before the umbrella was dismantled), not a one-directional import: `CrawlController` injects `JobQueueService` (to submit/poll/cancel jobs), and `JobWorkerService` injects `CrawlService` (to actually run them) — so `CrawlModule` imports `JobQueueModule` via `forwardRef()` and `JobQueueModule` imports `CrawlModule` via `forwardRef()` right back. Only the target module/service names and import paths changed when the umbrella was dismantled; the mutual `forwardRef()` shape itself didn't.
- **`opensearch/`** (`OpenSearchModule` registered directly in `AppModule` — nothing in the DI graph injects `IndexAdminService`/`OpenSearchService` from outside its own module, so unlike `crawl/`/`job-queue/` there's no `forwardRef()` pulling it in transitively) — manages the OpenSearch legal-provisions index: `IndexAdminService` (index/alias lifecycle — create, promote blue/green, drop) and `OpenSearchService` (backfill/reproject/search), both behind `OpensearchClientModule`'s `OPENSEARCH_CLIENT` token. Routes dropped the `/laws/index` prefix (`PUT /opensearch/index`, `GET /opensearch/status`, `POST /opensearch/backfill`, `POST /opensearch/reproject`, `PATCH /opensearch/aliases`, `DELETE /opensearch/index/:version`, `POST /opensearch/search`), swagger tag is `opensearch`. `opensearch.module.spec.ts` (new — didn't exist before the move) preserves the DI wiring-check coverage that used to live inside the now-deleted `law-index.module.spec.ts`'s "imports OpenSearchModule" test.
- The schema is **not** a verbatim copy of `docs/schema/legal-agent.dbml` — cross-checking the DBML against vbpl.vn's real UI found real gaps (missing `document` columns for Ngành/Lĩnh vực/Người ký/Chức danh; a `reference_type` enum too coarse to keep several of vbpl.vn's 13 distinct relation categories separate, including the `promulgates`/"công bố" relationship database-design.md §1a had explicitly left as an undecided open question; a `node_type` missing `phu_luc`). The DBML has since been revised to reflect the shipped schema — see the schema files' own comments for the specifics behind each deviation.
- `document_node` (the Điều/Khoản/Điểm/Phụ lục hierarchy tree) is implemented — `document-node.parser.ts` turns a document's scraped `fullText` into the tree, `document-node.repository.ts` persists it. Full text is still also kept flat in `document.rawSource` (jsonb) as an audit copy.

### `laws/` — the workflow-A dataset

Not source code — a data directory with 14 top-level tier folders (`01-hien-phap/` … `14-quyet-dinh-ubnd-cap-huyen/`) mirroring Điều 4 of Luật 64/2025/QH15, described in `laws/README.md`. `manifest.json` is the single tracking list for every downloaded file; `download-log.csv` is an append-only per-attempt HTTP log. Only `server/src/download/`/`server/src/catalog/` write here (not `crawl/`, which writes to Postgres instead) — treat manual edits to `manifest.json` as something that will drift from disk state.

### Config pattern

`@nestjs/config` with `registerAs` namespaces (`app`, `postgres`, `opensearch`, `neo4j`, `chromadb` in `server/src/config/configuration.ts`; `lawDownload`, `crawl`, `jobQueue`, `opensearchProjector` colocated in their own modules as `utils/law-download.config.ts`, `crawl/crawl.config.ts`, `job-queue/job-queue.config.ts`, `opensearch/opensearch.config.ts`), loaded globally in `AppModule` and validated by a single Joi schema (`env.validation.ts`). When adding a new external dependency, follow this pattern: a `registerAs` config factory + corresponding Joi keys, not ad-hoc `process.env` reads in services. `crawl/crawl.config.ts` exports `crawlConfig` under the `crawl` namespace — formerly `lawIndexConfig`/`lawIndex` (renamed when `law-index.config.ts` merged into `crawl/`); the underlying env var names (`VBPL_BASE_URL`, `LAW_INDEX_MAX_TIER`, etc.) were deliberately left unchanged, since that's an `.env`-compatibility question separate from the internal code naming. `drizzle.config.ts` (server root, pointing at `persistence/`) is the one exception to the whole pattern — it's a standalone CLI config for `drizzle-kit` migrations, which run outside Nest's DI and read `POSTGRES_*` via `dotenv` directly instead.

## Running a law-index scrape/backfill pass

When asked to scrape more documents into the law-index pipeline (e.g. "scrape tier N", "backfill the remaining X documents"), this is the workflow that's actually worked in practice — not just the happy-path endpoint list. ("Law-index" here names the overall workflow-B ingestion process, matching `docs/monitoring/law-index-*` filenames — it is no longer a code module; the endpoints below live on `crawl.controller.ts`, `server/src/crawl/`.)

**Endpoints that exist on this branch** (`crawl.controller.ts`): `POST /crawl/url` (one document from vbpl.vn — the primary per-document sync endpoint for this runbook; `POST /crawl/chinhphu/url` is the vanban.chinhphu.vn supplementary-source equivalent, out of scope for this vbpl.vn-focused runbook — see the `crawl/` Architecture bullet for why it's not a drop-in substitute, namely zero `document_reference` rows ever), `POST`/`PUT /crawl/batch` (up to 100 URLs per call — present on this branch, `fix/server-resilience`; **still absent on some other branches**, e.g. the branch this file was originally written against — don't assume it's available without checking `git branch`/grepping the controller first), `POST /crawl/all` (crawls the entire Trung ương sitemap, no tier/type filter, one long unbounded request — fine for a smoke test with `limit`, not for a targeted tier pass), `GET /crawl/search` (read-only filtered search against live vbpl.vn; falls back to a read-only vanban.chinhphu.vn search only when vbpl.vn returns zero matches — see the `crawl/` Architecture bullet's `FallbackSearchService` note — neither path persists anything), `GET /retrieve` (`retrieve.controller.ts`, `server/src/retrieve/` — a top-level module, not part of `crawl.controller.ts` — same filters against already-synced Postgres rows). Step 3 below still recommends individual `POST /crawl/url` calls, paced in small chunks, over `/crawl/batch` even where it's available — the reliability history in §6/§11 of the monitoring log is about the underlying sequential scrape loop itself, not the transport, so it applies the same way to either endpoint shape.

**1. Discover candidates.** Prefer `GET /crawl/search?documentTypes=[...]&issuingBodies=[...]`, paginated with `pageSize=100`. Two known-flaky spots in this endpoint, confirmed live (see `docs/monitoring/law-index-flagged-documents.md` §8): `keyword` search appears to ignore the query and return a fixed/stale result set regardless of input — don't rely on it; and some `documentTypes` values (confirmed on `"Hiến pháp"`) return `total: 0` or time out once `pageSize` is set, even when real matching documents exist. If a type search looks wrong, cross-check by fetching `https://vbpl.vn/sitemap.xml` directly (plain HTTP, no browser needed) — it's a sitemap index; the Trung ương block is `sitemap/1.xml` through `sitemap/12.xml`. Those files contain real, human-readable, diacritic-stripped slugs (e.g. `hien-phap-nam-1959--889`), so grepping for a keyword fragment is a reliable fallback for finding specific documents the search endpoint won't surface.

**2. Diff candidates against Postgres by `sourceUrl`, not citation — and never deduplicate multiple search results against each other by citation either.** The `crawl/search` response has a separate, confirmed mojibake bug (UTF-8 decoded as Windows-1252 somewhere in `VbplClientService.searchDocuments`) that corrupts every Vietnamese-diacritic field in the response — `citation`, `title`, `issuingBody`. `sourceUrl` is unaffected (vbpl.vn's own slugs are ASCII-only placeholders/ids) and is what actually drives the sync request, so match on `document.raw_source->>'sourceUrl'` in Postgres against the search results' `sourceUrl`, never on the corrupted `citation` string — this includes deduplicating a *merged* candidate list from more than one `documentTypes`/`issuingBodies` query, not just the final diff against Postgres. This bit a real backfill (`docs/monitoring/law-index-flagged-documents.md` §9): dozens of genuinely distinct pre-1976 documents share the literal citation `"Không số"`, and deduping a merged list by that corrupted field collapsed them down to one, silently dropping the other ~50 from the candidate list before the backfill ever tried them. If querying more than one type/filter combination for the same pass, keep each query's results (and each diff-against-Postgres) separate per query — don't merge-then-dedupe by anything but `sourceUrl`.

**3. Sync via `POST /crawl/url`, in small sequential batches — start with ~20 as a stability check, then continue in chunks of ~50, reporting results after each chunk before starting the next.** This project's own history (`docs/monitoring/law-index-flagged-documents.md` §6) has repeatedly hit reliability collapse on large unattended single-shot batches — page-cache degradation, escalating failure rates, orphaned Chrome processes from restarts without `enableShutdownHooks()`. A `POST /crawl/all` sized to hundreds of documents in one request is exactly the failure mode already documented there; don't repeat it. Before starting, verify the dev server is actually up (`curl http://localhost:3000/api`) — if a task resumes after a gap, assume it's died (machine idle, Docker restart) and restart it (`npm run start:dev`) rather than assuming.

**4. Between batches, remove both synced *and* permanently-skipped candidates from whatever pending list you're tracking** — not just the ones that got a new `document` row. `upsertDocument`'s citation-collision guard (`document.repository.ts`, see flagged-documents.md §4) returns `{ documentId: null, skippedReason }` for a document colliding with an already-`không còn hiệu lực` row under the same citation (common on pre-1990s "Không số"-citation documents) — this is a permanent, deterministic outcome, not a transient failure, so retrying it in the next batch just wastes a request. Track remaining candidates in a `docs/monitoring/law-index-pending-<name>-resync.csv` (same self-correcting-on-regeneration pattern as the existing pending-backfill CSVs referenced in the flagged-documents log) and delete it once the pass completes — don't leave a stale/empty tracking file around.

**5. After the pass completes, heal dangling references it may have created.** `POST`/`PUT /crawl/url` no longer heal `document_reference` rows left dangling (target not yet scraped) after every single call — that per-document heal was a full dangling-refs table scan repeated on every sync, removed as part of the scraper-resilience hardening (see `docs/plan/scraper-resilience-plan.md`). The batch/job endpoints (`POST`/`PUT /crawl/batch`, `POST /crawl/all`, `POST /crawl/search`) still heal once at the end on their own, but a pass driven by repeated individual `POST /crawl/url` calls — the pattern step 3 above actually uses — gets none of that safety net. Call `PATCH /sync/refs/all` (`sync.controller.ts`, `server/src/sync/` — a top-level module, not part of `crawl.controller.ts`) once after such a pass finishes to heal anything it made newly resolvable; skipping this step means references pointing at documents synced during the pass can stay dangling indefinitely.

**6. Log any new pipeline bug found along the way in `docs/monitoring/law-index-flagged-documents.md` + its sibling CSV**, following the existing per-section format (root cause, fix, regression test, example) — this file is the project's only record of law-index data-quality issues and is expected to be appended to, not just read.
