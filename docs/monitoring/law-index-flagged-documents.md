**Status: manually maintained.** Nothing in `server/src/law-index/` writes to this file (or the CSV below) automatically — see [Not yet automated](#not-yet-automated). Every record here was found by ad-hoc SQL spot-checks after a reindex pass, not by an automated check.

**How the two files split:** this file is the issue narrative — what went wrong, root cause, fix, DB impact, open follow-up. **[`law-index-flagged-documents.csv`](law-index-flagged-documents.csv)** holds one row per affected document, tagged with the `section` number it belongs to below. Append to both (never overwrite) when a future pass finds something new.

## 1. Annex content dropped by footer-strip logic

|                         |                                                        |
| ----------------------- | ------------------------------------------------------ |
| **Status**        | ✅ Resolved — 2026-07-30                              |
| **Found**         | First 50-document`document_node` reindex             |
| **Docs affected** | 2 (`section=1` in CSV)                               |
| **DB impact**     | `document_node` tree missing the annex text entirely |

**Root cause:** the parser's footer-stripping logic only resumed structured parsing on the literal word "Phụ lục". Annexes placed after the signature block with other labels (a QCVN technical standard, a "Biểu số" report form) were silently dropped in full.

**Fix:** generalized the footer-escape trigger (`ANNEX_RESTART_PATTERN` in `document-node.parser.ts`) to also recognize a re-stated Quốc hiệu header or a standalone "Biểu số/Mẫu số/QCVN/TCVN `<code>`" title line. Regression tests added; both documents' trees rebuilt from stored `fullText`.

**Example:** `46/2026/TT-BXD` — QCVN annex (~145KB) went from 0% captured to 96%.

## 2. Điều header without a period → zero nodes

|                         |                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Resolved — 2026-07-31                                                                   |
| **Found**         | `document_node` backfill for all Luật/Bộ luật documents                                |
| **Docs affected** | 17 (`section=2` in CSV)                                                                   |
| **DB impact**     | `document_node` tree entirely empty despite the document having real, parseable structure |

**Root cause:** older "Luật sửa đổi, bổ sung" amendment laws (1962–2019 in this batch) write their Điều header without a period — bare `"Điều 1"`, `"Điều 1:"`, or `"Điều 1 <heading>"`. `DIEU_KHOAN_PATTERN` required a literal period, so none of these matched.

**Fix:** made the separator after the Điều number optional (`[.:]?` instead of mandatory `.`). Regression tests added for all three punctuation variants; all 17 documents' trees rebuilt.

**Example:** `04/1998/QH10` — 0 nodes → 37 nodes built.

**Known follow-up:** `61/2014/QH13`'s tree now builds (177 nodes) but has a separate, unresolved shape defect — see [§7](#7-quoted-multi-khoản-replacement-text-mis-nested).

## 3. Attributes-tab content leaked into `fullText`

|                         |                                                                                                                                                                |
| ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Resolved — 2026-07-31 (a related backfill is still pending, see below)                                                                                     |
| **Found**         | Same Luật/Bộ luật backfill; recurred identically in the tier-3 (Pháp lệnh) 100-doc batch                                                                  |
| **Docs affected** | 8 (`section=3` in CSV) + 498 pending a related backfill (see below)                                                                                          |
| **DB impact**     | `document.rawSource.fullText` corrupted (305–440 chars of attributes-table text instead of real body); `document_node` build was meaningless on top of it |

**Root cause:** none of these 8 documents has a "Nội dung" (full-text) tab on vbpl.vn at all — confirmed live — only Thuộc tính / Lược đồ / Văn bản gốc / Tải về. vbpl.vn has no digitized body for them; the only source is a scanned file behind "Văn bản gốc". `extractScopeTitleAndFullText()` read whichever tab pane was `.ant-tabs-tabpane-active` unconditionally, assuming Nội dung was always the default-active tab — but for these 8, Thuộc tính was, so its table got captured as `fullText`. 100% deterministic (all 8 re-synced independently and reproduced identically), not a timing flake.

**Fix:** `extractScopeTitleAndFullText()` now checks for a tab with `data-node-key="toan-van"` before trusting the active pane; if absent, `fullText` is stored as real `null` instead of the wrong pane's text. `document.repository.ts` (`computeContentVersion`) and `document-node.repository.ts` (`syncNodes`) updated to treat `fullText === null` as a legitimately empty tree, not a parse failure. All 8 re-synced and verified (`fullText` is genuine JSON `null` via `jsonb_typeof`).

**Extended scope — original scanned document link now captured:** since these documents have no digitized text, the scanned PDF behind "Văn bản gốc" is the only usable content. That link exists for *every* document (not just these 8) and is now captured: `VbplClientService.fetchDocument()` loads a 4th tab (`?tabs=hien-thi-pdf`) and extracts filenames from the DOM; `buildOriginalDocumentUrl()` (`vbpl.parser.ts`) constructs the download URL against a public, unauthenticated MoJ-operated MinIO gateway (`.../api/qtdc/public/doc/minio/buckets/vbpl/{internalId}/{filename}/download`) — verified live across 3 filename styles. New `document.original_document_urls` column (`text[]`, migration `0004_cloudy_warhawk.sql`), folded into `computeContentVersion`'s hash so it also triggers a re-write on re-sync.

**⚠️ Pending backfill (not a new bug — scope, not correctness):** a corpus-wide re-sync of all 653 already-indexed documents to populate `original_document_urls` was started and manually stopped at 207/653 (18.7% and climbing failure rate) — the new 4th tab load was markedly less reliable than the original 3 (this is the same page-cache resilience gap fixed in [§6](#6-tier-3-100-document-pass--three-pipeline-bugs)). The **498 still-pending documents are tracked in [`law-index-pending-original-doc-resync.csv`](law-index-pending-original-doc-resync.csv)**, self-correcting on re-generation (`WHERE original_document_urls = '{}'`). The resilience fix in §6 should let a re-attempt complete, but it has not been re-run as of this writing.

**Example:** `35/2002/QH10` — `fullText` was a 305-char attributes table, now `null`. `106/2016/QH13` — confirmed `fullText: null` with `original_document_urls` correctly populated alongside it.

## 4. Citation collision: documents silently overwritten or permanently blocked

|                         |                                                                                                                                                                                                                                 |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | 🟡 Mixed — 2026-08-01: 4 Resolved, 66 Won't fix (tier 2); 2026-08-03: 4 more Won't fix (tier 1)                                                                                                                                |
| **Found**         | Rechecking vbpl.vn Luật/Bộ luật coverage against Postgres — a 74-document gap (70 Luật + 4 Bộ luật); recurred identically in the tier-1 (Hiến pháp) pass                                                               |
| **Docs affected** | 74 (`section=4` in CSV) — 70 tier 2 (Luật/Bộ luật) + 4 tier 1 (historical Hiến pháp)                                                                                                                                    |
| **DB impact**     | A later "Không số" document's sync silently overwrote an earlier one's`document` row (title, dates, `raw_source`, cascaded `document_node` tree, all replaced); 69 documents were structurally unable to ever be stored |

**Root cause:** `document.citation_id` is `UNIQUE`, and `upsertDocument` looked up "already synced?" purely by matching `citation_id`. Two ways vbpl.vn's older (pre-1998) corpus breaks that assumption:

- **"Không số" ("no number")** — every pre-Đổi Mới law is recorded under the literal citation string "Không số". 67 distinct real laws (1959–1997) share it; only whichever synced *last* survives.
- **Reused batch instrument numbers** — at least 2 cases where vbpl.vn assigned the same citation to two different laws passed in the same batch (`270B-NQ/HĐNN8`, `3-LCT/HĐNN7`).

**Decision — 66 confirmed "Hết hiệu lực toàn bộ" (fully expired): Won't fix, out of scope.** Rationale: (1) direct precedent — `server/src/law/` made the same call for the same pattern (commit `d441189`); (2) the real fix (loosening `citation_id UNIQUE`) would need re-validating every citation-keyed lookup in `document.repository.ts` for content with no bearing on current law; (3) it's a small, fully enumerated, documented boundary — revisit only if scope ever grows to historical/repealed-law research.

**3 documents turned out to still be "Còn hiệu lực" (in force)** — pulled out and fixed individually rather than accepted into the won't-fix decision, since excluding live law is a correctness bug, not a scope call. The original "Không số" occupant (`Luật Cải cách ruộng đất`) got the same treatment for consistency.

**Fix — now a permanent mechanism in `upsertDocument`, not a one-off:**

- A document is recognized as a re-sync of *itself* by matching `rawSource.sourceUrl`, not citation (citation alone can't disambiguate two "Không số" documents).
- A genuine collision against a document that is **not** "còn hiệu lực": skipped, not overwritten (`{ documentId: null, skippedReason }`).
- A genuine collision against a document that **is** "còn hiệu lực": disambiguated by appending vbpl.vn's internal id — `"<citation> (vbpl-<id>)"` — and inserted as its own row.

**Methodology note:** an unrelated mojibake bug in the crawl-search response (UTF-8 decoded as Windows-1252 somewhere in `VbplClientService.searchDocuments`) produced ~20 false "missing" entries in the first diff pass. Re-diffed using the ASCII-only internal id instead. Worth fixing separately in `vbpl.parser.ts`'s search-response handling — flagged here only because it caused a second investigation pass, not because it caused any actual indexing failure.

**Example:** `Luật Cải cách ruộng đất` (1953, id 1105) — renamed `Không số` → `Không số (vbpl-1105)`, resolved. `3-LCT/HĐNN7` (1981) — blocked by `Luật Tổ chức Tòa án nhân dân`'s identical citation, confirmed expired, won't fix.

**2026-08-03 — same mechanism hit tier 1 (Hiến pháp), 4 more Won't fix.** All 6 of vbpl.vn's Hiến pháp-typed documents (1946/1959/1980/1992/1992-sửa-đổi-2001, plus the current consolidated `52/VBHN-VPQH`, which has its own citation and isn't affected) share the literal "Không số" citation — same pre-numbering-era pattern as tier 2. `Hiến pháp năm 1946` happened to sync first and holds the slot; the other 4 are all confirmed `Hết hiệu lực toàn bộ` (each superseded by the next), so the same won't-fix rationale applies without a separate decision. Unlike tier 2's 66, this set is small enough (4 documents, the entire population) that it's worth naming explicitly rather than leaving implicit: `Hiến pháp năm 1959` (id 889, hết hiệu lực 1980-12-19), `Hiến pháp năm 1980` (id 1534, hết hiệu lực 1992-04-15), `Hiến pháp năm 1992` (id 11234, hết hiệu lực 2014-01-01), `Hiến pháp năm 1992 (sửa đổi, bổ sung năm 2001)` (id 22313, hết hiệu lực 2014-01-01) — none currently retrievable from Postgres by this pass; only reachable today via vbpl.vn directly.

## 5. `issuing_body` mis-attributed to the drafting ministry — a vbpl.vn data-quality issue

|                         |                                                                                                                                                                               |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Resolved for the 2 tiers found — 2026-07-31. ⚠️ Same-shape risk on other tiers not yet audited (see below)                                                              |
| **Found**         | Postgres tier audit (tier 2: Luật/Bộ luật); extended after the same pattern turned up in the tier-3 (Pháp lệnh) 100-document pass                                        |
| **Docs affected** | 5 confirmed (`section=5` in CSV) — 3 tier 2 (Luật/Bộ luật), 2 tier 3 (Pháp lệnh)                                                                                      |
| **DB impact**     | `document.issuing_body` legally impossible for the 5 confirmed rows; the same corruption could be silently sitting in already-indexed tier 4–7 documents today, undetected |

**Root cause — this is a vbpl.vn data-quality issue, not a law-index scrape bug.** vbpl.vn's own "Cơ quan ban hành" field sometimes reports the drafting/reviewing ministry instead of the body legally empowered to issue the document (confirmed live in every case found so far). Điều 4 of Luật 64/2025/QH15 restricts several document tiers to exactly *one* issuing body regardless of which ministry drafted the text — so the wrong value is always structurally detectable for those tiers by checking document type against Điều 4, independent of content. Confirmed wrong so far on tier 2 (`Luật`/`Bộ luật`/`Nghị quyết` → must be Quốc hội) and tier 3 (`Pháp lệnh`/`Nghị quyết` → must be UBTVQH).

**Same-shape risk, not yet audited.** Điều 4 restricts these trung-ương tiers to a single mandated issuer the same way tiers 2–3 are restricted — nothing has specifically checked them for this defect yet, so it may already be silently present in the DB:

- **Tier 4** — `Lệnh`, `Quyết định` → must be Chủ tịch nước
- **Tier 5** — `Nghị định`, `Nghị quyết` → must be Chính phủ
- **Tier 6** — `Quyết định` → must be Thủ tướng Chính phủ
- **Tier 7** — `Nghị quyết` → must be Hội đồng Thẩm phán Tòa án nhân dân tối cao

Tiers 8–9 (`Thông tư`/`Thông tư liên tịch`) are structurally different — the issuing body legitimately varies per document (which ministry/agency issued *this* Thông tư) — so this single-mandated-issuer guard pattern doesn't directly transfer, though scrape correctness for those tiers hasn't been separately verified either.

**Fix (currently scoped to the 2 confirmed tiers):** `correctQuocHoiIssuingBody` (`vbpl.parser.ts`), called from `parseAttributes` — a permanent guard, not a one-off patch. `Luật`/`Bộ luật` are corrected to "Quốc hội" unconditionally and `Pháp lệnh` to "Uỷ ban Thường vụ Quốc hội" unconditionally, since no other body can legally issue those types. `Nghị quyết` is ambiguous by itself (Chính phủ/UBTVQH/HĐTP/HĐND also issue nghị quyết), so it's only corrected when the citation carries the issuing body's own numbering (`QUOC_HOI_CITATION_PATTERN` / `UBTVQH_CITATION_PATTERN`). Built for Luật/Bộ luật first, then extended to Pháp lệnh once the tier-3 pass found the same pattern there. Extending the same guard to tiers 4–6 (each single-issuer, same shape) is the natural next step but hasn't been done — tier 7 would need its own audit first since no document in this pass has touched Nghị quyết của Hội đồng Thẩm phán TANDTC yet.

**Three gotchas caught during rollout:**

- **Re-sync had no effect at first.** `computeContentVersion` hashed `fullText`/`citation`/`title`/validity/dates but not `issuingBody`, so an otherwise-unchanged document short-circuited the upsert before the correction was ever written (confirmed live: a re-sync returned `changed: false`, DB row untouched). Added `issuingBody` to the hash so an attribute-only correction can't be silently swallowed on re-sync.
- **A latent regex bug, fixed proactively before it hit a live document.** `QUOC_HOI_CITATION_PATTERN` (`/QHK?\d+$/i`) also matched UBTVQH citations, since both end in `QH<khóa>` (`"11/2016/UBTVQH13"`) — a UBTVQH-issued Nghị quyết would have been misclassified as Quốc hội's. Added a negative lookbehind excluding any citation where a letter immediately precedes "QH", and check the UBTVQH-specific pattern first.
- **Spelling gotcha:** vbpl.vn (and existing DB rows) spell it `"Uỷ ban Thường vụ Quốc hội"` — the guard's canonical string must match byte-for-byte or `resolveOrCreateIssuingBody` creates a duplicate `issuing_body` row instead of resolving to the existing one.

Regression tests added in `vbpl.parser.spec.ts` for both bodies and the citation-pattern fix.

**Example:** `149/2025/QH15` — corrected from "Bộ Tài chính" to "Quốc hội". `11/2016/UBTVQH13` — corrected from "Quốc hội" to "Uỷ ban Thường vụ Quốc hội".

## 6. Tier-3 100-document pass — three pipeline bugs

|                         |                                                                                                                                                                                                                                                           |
| ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Resolved — 2026-07-31; follow-up bugs found 2026-08-03 also resolved                                                                                                                                                                                  |
| **Found**         | Running the first 100 Pháp lệnh (tier 3) documents end to end; the 3 follow-up bugs (6d) surfaced re-attempting §3's corpus-wide backfill                                                                                                              |
| **Docs affected** | 2 direct data-loss cases (`section=6` in CSV); the page-cache fix (6b) and the two 6d fixes each protect/affect every future crawl — the internal-id bug alone silently affected ~7% of the corpus (48/653 documents) for `original_document_urls`   |
| **DB impact**     | `document_node` silently missing on 2 documents; search results silently truncated below the requested `pageSize`; `original_document_urls` silently staying empty on real slug-URL/UUID-id documents even after an apparently-successful sync (6d) |

Four distinct findings surfaced in `server/src/law-index/crawl/`, listed in the order found:

**6a. `pageSize` filter silently ignored.** `VbplClientService.searchDocuments`'s `selectPageSize()` ran *before* the filtered search was submitted, against the page's initial unfiltered list — so vbpl.vn reset back to its default (10/page) the moment the real search ran. A `pageSize=100` request silently came back as 10 items, no error. **Fix:** moved `selectPageSize()` to after the search submits and re-waits, before the page-jump step. Verified live.

**6b. Stuck/broken Playwright page had no recovery path.** `getPage()` cached its browser page indefinitely with no health check. ## 7. Quoted multi-Khoản replacement text mis-nested

|                         |                                                                                                                                                                                                                              |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ⚠️ Unresolved                                                                                                                                                                                                              |
| **Found**         | 2026-07-31, while investigating[§2](#2-điều-header-without-a-period--zero-nodes)                                                                                                                                           |

**Root cause:** this is a parser shape issue, not a per-document data problem — it isn't a bounded checklist the way §1–3 are. **Needed:** track quote-open/quote-close state across lines (open on a leading `"`/`"`, close on a trailing `"`/`"`) so everything inside a quoted span is treated as opaque text of the node that opened the quote, regardless of what it looks like structurally. Not attempted yet. Likely affects other "Luật sửa đổi, bổ sung" documents beyond the one confirmed case — actual scope not surveyed.

**Update, 2026-08-05 — corpus-wide scope found; see §12c, in [§12](#12-duplicate-document_node-paths--phase-0-of-the-opensearch-projector-plan-three-distinct-causes).** Auditing `document_node` for path uniqueness ahead of the OpenSearch projector found this same phenomenon (quoted replacement text carrying its own numbering) is not a 1-document edge case — it's one of two causes behind 597 documents' worth of duplicate `(document_id, path)` rows. §12c covers the corpus-wide finding and the uniqueness backstop that was added; it does not fix the mis-nesting this section describes, which remains open.

## 9. Cross-search citation dedup silently undercounted the tier-3 backfill

|                         |                                                                                                                                                                                                                  |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Resolved — 2026-08-03                                                                                                                                                                                        |
| **Found**         | Investigating an unrelated apparent "document count regression" after the tier-3 backfill above — the regression itself turned out to be a red herring (see below), but investigating it surfaced this real bug |
| **Docs affected** | 56 (54 Pháp lệnh + 2 Nghị quyết)                                                                                                                                                                             |
| **DB impact**     | None — no wrong data was ever written. The backfill pass above just silently never attempted these 56 documents, so they were simply absent, not corrupted.                                                     |

**Root cause:** the ad-hoc script that built the tier-3 backfill's candidate list searched `documentTypes=["Pháp lệnh"]` and `documentTypes=["Nghị quyết"], issuingBodies=["Uỷ ban Thường vụ Quốc hội"]` separately, then merged the two result sets and deduplicated by each item's `citation` field before diffing against Postgres. `citation` in a `crawl/search` response is corrupted by the same mojibake bug noted in §4's methodology note (UTF-8 decoded as Windows-1252 somewhere in `VbplClientService.searchDocuments`) — and critically, this corruption is *lossy*, not just cosmetic: many genuinely distinct pre-1976 documents share the literal citation `"Không số"`, and the corrupted rendering of that string collided across all of them in the dedup `Map`, so only the first-seen one survived the merge. The other 53 silently vanished from the candidate list before the backfill ever got a chance to attempt them (2 more were lost the same way from the Nghị quyết side, on a smaller "Không số" cluster there).

**How it was found:** a routine re-check of document counts after the backfill appeared to show 2 rows had vanished from the DB (136 Pháp lệnh right after the backfill → 135 later) with no corresponding write activity — first suspected as a possible external/manual deletion (Postgres logs do show an unrelated, unsuccessful manual `DELETE FROM document` attempt from 2026-07-31, proving direct DB access happens in this environment, but no evidence tied it to this specific delta). That theory turned out to be a wrong track: a clean, single-type re-diff (`documentTypes=["Pháp lệnh"]` alone, matched against Postgres by `sourceUrl` rather than any merged/deduplicated candidate list) immediately revealed the real gap was 54, not 1 — proving the "1-2 row disappearance" observation was just noise on top of a much larger, pre-existing undercount, not a real deletion event.

**Fix — methodological, not code:** re-ran the candidate search per-type (no cross-type merge), diffed each type's results against Postgres independently by `sourceUrl`, and synced the union of gaps directly. No production code changed — `crawl/search`'s underlying mojibake bug (§4) is still unfixed and still corrupts response text; the fix here is procedural: **never deduplicate `crawl/search` results by `citation` across multiple queries — dedupe (or diff against Postgres) by `sourceUrl` only.** This is now called out explicitly in the root `CLAUDE.md`'s law-index scraping runbook.

**Example:** of the 54 recovered Pháp lệnh documents, 44 turned out to be additional `"Không số"`-citation collisions against already-expired documents (correctly skipped, not overwritten — the §4 mechanism working as designed on a larger cluster than previously seen) and 10 were genuine new rows, including several pre-1976 `"Không số"`-citation Pháp lệnh that vbpl.vn marks `còn hiệu lực` (still in force) and which the disambiguation path (§4) correctly inserted as `"Không số (vbpl-<id>)"`.

Three distinct root causes, found auditing `document-node.parser.ts` against the live corpus rather than assumed from the symptom alone:

**12a. A repeated "Phụ lục N" running header mis-opened as a new sibling annex — RESOLVED.** Real appendices restate their own "Phụ lục I"-style header once per subsection (a page-header artifact of whatever produced the source document vbpl.vn digitized), not once per document. `parseDocumentBody`'s `if (phuLucNode)` branch treated every line matching `PHU_LUC_PATTERN` as opening a new annex regardless of whether the numeral matched the one already open — `openPhuLucFromMatch` computed `ordinal = romanToArabic(match[2])` fresh each time, so 21 repetitions of "Phụ lục I" all produced ordinal `"1"` and collided on the same ltree path. **Fix:** a repeated header whose numeral equals the currently-open annex's raw (pre-dedup) ordinal is now folded into that annex's body text instead of opening a sibling; a genuinely different numeral still opens a new one. Regression tests added (`document-node.parser.spec.ts`) for both the fold case and the genuine-new-annex case. **Example:** `22/2026/NQ-CP` — 21 duplicate "Phụ lục I" nodes → 1 node with all 21 subsections' text concatenated.

**12b. Tabular/statistical data misread as Khoản numbering — UNRESOLVED (root cause).** `KHOAN_PATTERN` (`^(\d+)([a-zđ]?)\s*\.\s*(.*)$`) matches any line starting with `<digits>.`, which real Khoản numbering isn't the only Vietnamese legal-document content shaped like. Land-use planning Nghị quyết embed large statistics tables (loại đất, diện tích) flattened to plain text by the scrape; decimal classification codes (`"1.1.1.1 Đất chuyên trồng lúa nước"`) and table row/column values match the pattern on their leading digit group, all landing on ordinal `"1"` (the pattern only captures the first digit group before the first `.`, discarding the rest as body text) and colliding under the same Điều. **Example:** `25/2007/NQ-CP` — 126 duplicate "Khoản 1" nodes under `dieu2.khoan1`, containing land-classification codes and bare area figures (`"668"`, `"555"`), not real clauses. **Needed, not attempted:** a way to recognize this content is a table rather than clause text — out of scope for a line-based regex parser without a captured real sample set to calibrate a heuristic against (same posture as every other rule in this parser).

**12c. Quoted "sửa đổi ... như sau: `<text>`" replacement text carries its own independent numbering — extends [§7](#7-quoted-multi-khoản-replacement-text-mis-nested) with corpus-wide scope.** §7 documented this shape (an amending Điều quoting a target document's replacement text, itself numbered) as a tree-shape defect on one confirmed document. This audit found it's the dominant cause behind the `khoan`/`diem` duplicate count — every quoted excerpt restarts its own numbering at 1 independently of the amending document's real structure, and when multiple excerpts (or the excerpt plus the amending Điều's own "1. Sửa đổi ... như sau:" preamble) land under the same parent, they collide. **Example:** `07/2022/NĐ-CP`, Điều 1 Khoản 1 — 7 duplicate "Khoản 1" nodes: the real preamble ("Sửa đổi, bổ sung một số khoản của Điều 3 như sau:") plus 6 unrelated quoted fine-amount clauses from the target decree, each independently numbered "1." in the source. `12/2017/QH14` (a Luật sửa đổi Bộ luật Hình sự) shows the same shape at larger scale — 82 duplicate groups, worst single group 99 copies. §7's fix (quote-open/quote-close tracking) is still what would resolve this properly; not attempted here.

**12b/12c fix implemented, 2026-08-08 — RESOLVED, including the broadened vocabulary found above.** `document-node.parser.ts` now suppresses both shapes at parse time instead of only disambiguating the resulting collision:

- **12b (`inTable`):** `TABLE_HEADER_PATTERN`/`TABLE_HEADER_ABBREV_PATTERN` recognize a standalone header-row line (`Đơn vị tính`, `Thứ tự`/`Số thứ tự`, `Loại đất`, `Bậc`, case-sensitive `STT`/`TT`) and set an `inTable` flag, mirroring `inFooter`'s existing shape exactly — every line is appended as inert body text on the enclosing node until a container-level heading (Điều/Chương/Mục/Tiểu mục/Phụ lục) resets it.
- **12c (`quoteDepth`/`pendingQuoteCitation`):** a citing line containing a verb (`sửa đổi`/`bổ sung`/`bãi bỏ`/`thay thế`, **no "được" or "như sau" required** — broadened per the curly-quote/bare-colon findings above) and ending in `:` arms `pendingQuoteCitation`; if the *next* line starts with an opening quote (straight `"` **or** curly `"`, both now tracked, closing on `"`/`"`/parity), every subsequent line is suppressed as body text on the citing node until the quote's depth returns to 0. A line ending `:` with no quote on the following line is a no-op — the citing-verb check is a cheap safety margin, not the real gate, so a false match costs nothing.
- Deliberate trade-off, documented in code: suppression is checked *before* container-level patterns, so a quoted target Điều heading (e.g. `"Điều 17c. ...`) correctly stays suppressed rather than opening a fake sibling — but a quote that never closes (malformed source) would suppress the rest of the document rather than recovering at the next real heading. Not observed in any real sample; no safety-net cap added for it.

**Client-tooling lessons from this specific backfill run, kept here rather than in a second document since they explain how the 104/2026/NĐ-CP race actually happened:**
- **`PUT /crawl/batch` is fully synchronous** — it returns nothing until every URL in the request has been processed, no streaming. At the observed ~30–60s/document rate, a 50-document batch can run 25–50 minutes in one request.
- **Node's global `fetch()` enforces its own internal 300s `headersTimeout`** (via undici) regardless of any `AbortSignal` passed to it — an `AbortSignal.timeout(90min)` does **not** override it; the client throws `UND_ERR_HEADERS_TIMEOUT` at 300s either way. A custom dispatcher is needed. `require('undici')` for that dispatcher is also not reliable outside a directory with `server/`'s own `node_modules` in its ancestry (`node:undici` is not a real built-in on the Node version used here) — the robust fix was dropping `fetch` entirely for this tooling and using `node:http` directly, whose `timeout` option is a plain idle-socket timeout with no hidden ceiling.
- **`nest start --watch`'s file watcher is not scoped to `sourceRoot` ("src")** — it reacts to changes anywhere under the project directory. Ad-hoc scratch scripts/tracking files for a backfill should live outside `server/` entirely (this pass moved them to the session scratchpad after noticing a `File change detected... ## 13. `sanitizeOrdinalForLtree` silently stripped the Vietnamese letter `đ` — a repository-layer bug, not a parser one

|                         |                                                                                                                                                                                                                              |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Fully resolved — 2026-08-07; code fix, the 7 collision documents, and the remaining precision-only documents are all re-synced. See §14 for a performance bug this pass's re-sync surfaced (fixed the same day). |
| **Found**         | 2026-08-06, auditing batch 2 of the §12 backfill — one document (`17/2017/QH14`) still showed duplicate paths *after* an isolated, non-concurrent re-sync, ruling out §12's race-condition explanation                 |
| **Docs affected** | 7 with real path collisions (`document_reference`-worthy data-integrity issue); 1,434 total containing at least one bare `đ` Điểm (cosmetic `path` precision only, no duplication)                                     |
| **DB impact**     | 10 `document_node` rows across 7 documents shared a `path` with an unrelated sibling; ~12,400 unrelated `Điểm đ` rows had a `path` segment indistinguishable from "no ordinal at all" (content itself was never wrong) |

**Root cause, and why it's a different bug from §12.** `sanitizeOrdinalForLtree` (`document-node.repository.ts`) built the ltree `path` segment by stripping every character outside `[A-Za-z0-9_]` — including `đ`, a real, common Vietnamese-alphabet ordinal letter that `document-node.parser.ts`'s own `[a-zđ]` character class has always accepted (both for a plain "đ)" Điểm — 5th point in an a/b/c/d/đ/**đ**/e... list — and for the rarer inserted-provision suffix case, "Điều 146đ", per Điều 69.4, Nghị định 78/2025/NĐ-CP). The function's own comment asserted ordinal was "already ASCII alphanumeric by construction" — wrong, and directly contradicted by the parser file it cited.

This produces two distinct symptoms:
- **Real path collision:** `"146đ"` sanitizes to `"146"`, identical to the unrelated, already-existing `"Điều 146"`. Confirmed on 10 rows across 7 documents (`13/2022/NĐ-CP`, `17/2017/QH14` ×3, `21/2026/NĐ-CP`, `34/2025/NĐ-CP`, `37/2024/QH15`, `74/2006/QH11` ×2, `78/2025/QH15`). Unlike §12, no re-sync — however clean or isolated — can fix this; the bug is deterministic, not timing-dependent.
- **Cosmetic precision loss:** a bare `"đ"` Điểm sanitizes to `""`, so its path segment is just `"diem"` — indistinguishable in the `path` column from a node with no ordinal at all. Confirmed on ~12,400 rows across 1,434 documents. **Not a duplication bug** — a Vietnamese Điểm list has at most one `đ` per list, so this practically never collides with a sibling (confirmed empirically: 0 of the duplicate-path groups found anywhere in this project trace back to a bare `đ` alone). `document_node.ordinal`, `.label`, and `.text_content` were never affected — the content was captured correctly the entire time; only the derived `path` column lost precision.

**Fix:** `sanitizeOrdinalForLtree` now transliterates `đ`/`Đ` to `"dd"` before stripping, via a small `VIETNAMESE_ORDINAL_TRANSLITERATION` lookup (extensible if the parser's accepted suffix charset ever grows past `đ`), rather than dropping it. `"dd"` was chosen deliberately over the more obvious `"d"`: a real `"d)"` Điểm and a real `"đ)"` Điểm are commonly adjacent siblings in the same list (a/b/c/**d**/**đ**/e), so transliterating to plain `"d"` would have traded one collision for a more common one. The function is now exported and covered by a dedicated `document-node.repository.spec.ts` (7 tests) — the first spec for this repository in this worktree, added following the codebase's existing convention of keeping logic pure/DI-free specifically so it stays unit-testable, even though `sanitizeOrdinalForLtree` itself needed no DI to begin with (it just wasn't exported).

**Re-sync scope, done in two passes:**
- **7 collision-causing documents — re-synced 2026-08-06**, since they were already part of the active §12 backfill batch and blocking that batch's own gate check.
- **The remaining bare-`đ`/`Đ` documents — re-synced 2026-08-07, without re-scraping vbpl.vn.** These were never part of §12's 636-document duplicate-path list (bare `đ` doesn't duplicate), so folding them into that backfill would have silently ~tripled its scope without being asked for — hence the original deferral, tracked in `law-index-pending-dd-ordinal-precision-resync.csv`. Since `sanitizeOrdinalForLtree`'s output is the *only* thing that changed — `document.rawSource->>'fullText'` was already captured by the original scrape and the parse of it hadn't changed — a one-off script (`scripts/resync-dd-ordinal-precision.ts`, removed after use) called `DocumentNodeRepository.syncNodes()` directly against each affected document's already-stored `fullText`, with no network/Playwright/vbpl.vn involved. A live, case-insensitive re-check (`ordinal ~* 'đ'`) turned up 1,436 documents rather than the originally-estimated 1,427 — the gap is 21 rows with an uppercase `Đ` ordinal the original (lowercase-only) audit query missed, now covered by the same case-insensitive fix. The CSV is deleted; this pass is complete.

**Verification:** 135/135 tests pass (7 new). Live: `17/2017/QH14`, after the code fix and one re-sync, dropped from 14 duplicate `(path, node_type)` groups to 0. After the 2026-08-07 pass: 0 documents remain with an `ordinal ~* 'đ'` row whose `path` doesn't reflect the `dd` transliteration, and the corpus-wide `(document_id, path, node_type)` duplicate check (§12's own gate query) still returns 0.

## 14. Missing indexes on `document_node`/`document_reference` FK columns made every `syncNodes()` delete an O(corpus size) operation

|                         |                                                                                                                                                                                                                              |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Resolved — 2026-08-07, migration `0007_add_missing_fk_indexes.sql`                                                                                                                                                    |
| **Found**         | 2026-08-07, running the §13 precision re-sync — a single 1,636-node document's `syncNodes()` delete step was still running after 3+ minutes, caught mid-flight via `pg_stat_activity`                                  |
| **Docs affected** | None directly (no data was ever wrong) — this is a performance defect in every document re-sync, scaling with both corpus size and the size of the document being re-synced                                            |
| **DB impact**     | None — additive indexes only, no rows changed                                                                                                                                                                              |

**Root cause.** Three `document_node` columns (`document_id`, `parent_id`, `superseded_by_node_id`) and two `document_reference` columns (`source_node_id`, `target_node_id`) are foreign keys with no supporting index — only `document_reference.source_document_id`/`target_document_id` had one (added in migration `0006`). `DocumentNodeRepository.syncNodes()`'s `DELETE FROM document_node WHERE document_id = $1` therefore paid twice: the `WHERE` lookup itself was a sequential scan of the full table (no index on `document_id`), and Postgres's own per-row referential-integrity check — confirmed live via `pg_stat_activity` catching the exact query `SELECT 1 FROM document_node WHERE parent_id = $1 FOR KEY SHARE` — is *also* a full sequential scan per row deleted, since `parent_id` has no index either. For a document with N nodes, that's roughly N sequential scans of a 507K-row table, on top of the initial one. This has always been true of `syncNodes()`, not something newly introduced — it only surfaced now because the §13 re-sync was the first time this many large documents got re-synced back-to-back outside a live scrape (where the ~1s/request throttle and Playwright's own latency had been masking how slow the DB side was).

**Fix.** Migration `0007_add_missing_fk_indexes.sql` adds plain B-tree indexes on all five columns. Confirmed live: the same 1,636-node document that hadn't finished after 3+ minutes pre-fix completed in under 9 seconds post-fix (including `ts-node` cold-start overhead). Schema files (`document-node.schema.ts`, `document-reference.schema.ts`) updated to match, using the `pgTable(..., (table) => [...])` extraConfig-callback form — see those files' own comments on why a standalone `index(...).on(table.column)` export crashes on this drizzle-orm version.

**Aside: `drizzle-kit generate` is currently unusable due to unrelated pre-existing drift**, found while adding this migration — `migrations/meta/_journal.json` had a missing comma and a stray trailing comma (another bad-merge artifact, same class as the ones already fixed elsewhere this session), and `migrations/meta/0006_snapshot.json` doesn't exist at all even though `0006_quick_shockwave.sql` does and its indexes are live in the database — migration `0006` was applied to the database by some means other than `npm run db:migrate` (confirmed: `drizzle.__drizzle_migrations` has no row for it). This migration (`0007`) was therefore hand-written (matching `0006`'s own style) and applied directly via `psql` rather than through `drizzle-kit generate`/`db:migrate`, both to sidestep the corrupted journal and because a snapshot-based diff against a database state `drizzle-kit` doesn't think exists would likely regenerate `0006`'s already-applied indexes a second time and fail. The `_journal.json` corruption is fixed as a side effect of adding this entry; the missing `0006_snapshot.json` and the untracked `0006` migration row are not — worth a follow-up before the next schema change needs `drizzle-kit generate` to produce a clean diff.

**Verification:** `\d document_node` / `\d document_reference` show all 5 new indexes live. §13's 1,436-document re-sync (which exercises this exact code path at scale) completed without incident afterward.

## 15. vbpl.vn's "Điều khoản được sửa đổi, bổ sung" amendment-annotation rendering duplicates and reorders Khoản content — a 5th distinct cause of the §12 symptom, found via the OpenSearch projector

|                         |                                                                                                                                                                                                                              |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Resolved — 2026-08-07, fixed at extraction time (not the projector) and all 216 documents re-synced                                                                                                                  |
| **Found**         | 2026-08-07, syncing Postgres → OpenSearch — the projector surfaced a Điều with `khoan.label = ["Khoản 1", "Khoản 2", "Khoản 2"]`, traced back to Postgres and then to the raw scrape                                    |

| **DB impact**     | None beyond what §12's existing backstop already produces: a `_2`/`_3`-suffixed `ordinal`/`path` keeping Postgres unique, with `label`/`text_content` genuinely reflecting two different, real pieces of scraped text     |

**Root cause.** vbpl.vn renders an "Điều khoản được sửa đổi, bổ sung" ("this clause has been amended/supplemented") annotation inline before each amended Khoản, for documents with amendment history — confirmed live on `38/2005/QH11` (Luật Giáo dục 2005). For Điều 41 specifically, the raw scraped `fullText` reads:

```text
Điều khoản được sửa đổi, bổ sung
Điều 41. Chương trình, giáo trình giáo dục đại học

2. Giáo trình giáo dục đại học cụ thể hóa...          ← Khoản 2 (first copy)

Điều khoản được sửa đổi, bổ sung
```

Khoản 2's real text appears twice and Khoản 1 appears once but out of its natural numeric position — already present in the raw scrape, before `document-node.parser.ts` ever runs. This is distinct from every other cause on this page: not §12a (repeated Phụ lục header), not §12b (tabular data misread as numbering), not §12c (a *different* document's quoted replacement text carrying its own numbering), and not §4/§12's race condition (which produces *identical*, unsuffixed ordinals from two independent insert loops — here the ordinal is `2_2`, the parser-backstop signature, and the two nodes' `content_hash` genuinely differ). **Re-sync:** all 216 documents re-synced via `PUT /laws/index/crawl/url|batch?force=true` (this genuinely required re-scraping vbpl.vn, unlike §13 — the bug was in what got captured into `document.rawSource.fullText`, not in how already-stored text gets processed). 0 errors, 0 not-found, corpus-wide duplicate-path count held at 0 throughout. Confirmed impact: the corpus-wide count of documents/rows carrying a `dedupeOrdinal` backstop suffix (any cause) dropped from 629 documents / 31,315 rows to 591 / 31,144 — the 38-document / 171-row difference is this fix's real, resolved footprint; the remaining 591 documents are attributable to the still-open §12b/§12c causes.

## 16. Some documents' scraped text is Unicode NFD instead of NFC, silently breaking every diacritic pattern match

|                         |                                                                                                                                                                                                                              |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Status**        | ✅ Resolved — 2026-08-08, fixed at parse time (not extraction) and all 171 affected documents re-synced, same day as it was found                                                            |
| **Found**         | 2026-08-08, root-causing `368/2025/NĐ-CP` (a document whose collision showed an entire Điều's content absorbed into the previous one, despite its `"Điều 6."` heading looking perfectly well-formed at a glance)      |
| **Docs affected** | 171 of 3,338 (5.1%, was 173 at discovery — 2 shifted to NFC incidentally during the same day's unrelated §12b/§12c backfill) corpus-wide confirmed via `normalize(fullText, NFC) <> fullText`, all re-synced; 38 of these were among the 364 duplicate-path documents (produced a *visible* collision), the other 133 showed no path-collision symptom but were equally exposed |
| **DB impact**     | Not extrapolated to a row count precisely — unlike 12b/12c/15, this cause didn't reliably produce a *detectable* symptom before the fix (see below), so the usual "duplicate-path groups" metric always understated its real footprint. Post-fix: corpus-wide backstop-suffixed document count dropped 273 → 242 (31 documents' visible collisions resolved directly; the rest of the 171 had no visible symptom to begin with, so aren't reflected in that metric)                |

**Root cause.** `document-node.parser.ts`'s structural patterns (`DIEU_KHOAN_PATTERN`, `KHOAN_PATTERN`, `DIEM_PATTERN`, `PHU_LUC_PATTERN`, etc.) are literal-string/regex matches against Vietnamese diacritic characters, written in the source file as Unicode NFC (precomposed — e.g. `"ề"` = single codepoint U+1EC1). Some documents' `document.raw_source.fullText` is instead Unicode NFD (canonically-decomposed — the same visible glyph built from a base letter plus one or more combining marks, e.g. `"ề"` = `U+00EA` (`ê`) + `U+0300` (combining grave accent)). NFC and NFD render identically and are canonically equivalent, but they are **not** the same codepoint sequence, so a regex written against NFC literals silently fails to match NFD input — with no error, no exception, just a heading the parser never recognizes as a heading.

Confirmed directly on `368/2025/NĐ-CP`: dumping the raw bytes of its `"Điều 6. Các hành vi bị cấm"` heading line found every diacritic decomposed (`Đ-i-ê+◌̀-u` for "Điều", `c-â+◌́-m` for "cấm", etc.) — a completely normal-looking, correctly-spaced heading that `DIEU_KHOAN_PATTERN` nonetheless never matched, because the pattern's own literal `"Điều"` is NFC. The practical effect: parsing never closed the "Điều 5" node, so all of Điều 6's Khoản 1–6 ("Các hành vi bị cấm" — prohibited acts) got absorbed as extra Khoản siblings of Điều 5's own Khoản 1–2, restarting the ordinal count and colliding (`document_node` for this document has no `dieu6` node at all — confirmed by querying its tree directly, not inferred).

This is a **different failure mode from the already-logged missing-space bug** (§12's "`Điều106.`" note, above) — that one fails `DIEU_KHOAN_PATTERN`'s `\s+` requirement on a genuinely malformed heading; this one fails on a heading that is, character-for-character as a human or a Vietnamese-locale-aware tool would read it, perfectly well-formed. It's also the reason `12/2017/QH14` — the plan document's own headline 12c example — was never actually in the 227-document 12b/12c CSV: its citing sentences (`"Sửa đổi, bổ sung khoản 3 Điều 95 như sau:"`) use decomposed diacritics too, which incidentally also broke the curly-quote-based 12c signal search, but the real reason the whole document's structure is wrong is this NFD mismatch, not a quote-style variant.

**Why this is more severe than 12b/12c/15:** those three causes are all *self-limiting* — they only ever produce a **duplicate** ordinal (a real Khoản/Điểm sibling collides with a fake one from a table row, a quoted excerpt, or a shadow DOM node), which the `dedupeOrdinal` backstop reliably catches and which this project has been using as its detection signal throughout (`ordinal ~ '_[0-9]+$'`). An NFD-broken heading match has **no such guarantee** — whether it produces a visible collision depends entirely on whether the absorbed section's own Khoản numbering happens to overlap with the section it got merged into (as it did here: Điều 6 also had a "Khoản 1"/"Khoản 2", colliding with Điều 5's). A document where the absorbed section's Khoản numbers *don't* overlap (e.g. Điều 5 has only 1 Khoản, Điều 6 starts its own count at 1 anyway — coincidentally always true for this pair, but not guaranteed in general) would show **zero** duplicate-path symptoms while still having a completely wrong tree — content that belongs under its own `Điều 6` node silently living under `Điều 5` instead, undetectable by any check this log has used so far. This is why 135 of the 173 NFD-affected documents currently show no collision at all: it isn't evidence they're fine, only that this particular audit's detection method (the dedupeOrdinal backstop) can't see this class of damage.

**Scope pattern:** the NFD rate is heavily skewed toward recent enactment years — 2022–2026 average ~12% NFD-affected (13/77 in 2022, 10/58 in 2023, 13/134 in 2024, 10/401 in 2025, 15/280 in 2026) versus 5.2% corpus-wide — suggesting this is tied to some more-recent change in how vbpl.vn serves certain pages (a CMS change, a different authoring/upload pipeline for newer documents) rather than an artifact of old OCR'd scans, which would be expected to skew the other way (older documents more likely decomposed from legacy digitization tooling). Not confirmed against vbpl.vn's own systems — inferred from the corpus's own date distribution only.

**Fix, implemented 2026-08-08 — a single normalization point, not a rewrite of every pattern.** `parseDocumentBody()` (`document-node.parser.ts`) now calls `fullText.normalize('NFC')` once, right before line-splitting — the option this section's original draft called the cheaper path (over normalizing at extraction in `vbpl-client.service.ts`), for the same reason §13 preferred re-parsing already-stored text over re-scraping: `String.prototype.normalize('NFC')` is a pure, lossless transform, so this single choke point fixes both already-stored documents (re-parseable from `document.raw_source.fullText` with **no re-scrape needed**) and any future scrape, since this function is the sole entry point from raw text to the node tree either way. `document.raw_source.fullText` itself is deliberately left untouched (still whatever normalization form vbpl.vn actually served) — same posture as §13, which never rewrote the stored audit copy either, only what gets derived from it.

**Regression test:** `document-node.parser.spec.ts` reproduces the exact `368/2025/NĐ-CP` shape — a fixture built from an ordinary NFC string via `.normalize('NFD')` (no hand-typed decomposed Unicode needed), asserting the "Điều 6" heading still opens its own node rather than being absorbed into "Điều 5". 31/31 parser tests pass (1 new), 514/514 full suite.

**Re-sync:** all 171 currently-affected documents re-synced via a one-off script (`scripts/resync-nfd-normalization.ts`, removed after use, same disposable-script convention as §13's) that calls `DocumentNodeRepository.syncNodes()` directly against each document's already-stored `raw_source.fullText` — no network/Playwright/vbpl.vn involved, matching the "no re-scrape needed" design above. 171/171 succeeded, 0 failures. Confirmed live: `368/2025/NĐ-CP` now has a correct `chuong1.dieu6` node (`heading = "Các hành vi bị cấm"`) that didn't exist pre-fix. Corpus-wide gate (`(document_id, path, node_type)` duplicates) held at 0 throughout; the backstop-suffixed document count dropped 273 → 242. The other ~133 re-synced documents had no visible collision before or after (that was the whole point of this section) — their fix isn't independently visible via that metric, only via the underlying tree now being structurally correct (spot-checked on `368/2025/NĐ-CP` only, not exhaustively re-verified per document, consistent with this log's usual verification depth for a 100+ document pass).

**Verification method (for reproducing the affected-document count):** `SELECT count(*) FROM document WHERE normalize(raw_source->>'fullText', NFC) <> (raw_source->>'fullText');` — requires Postgres 15+ (`normalize()` SQL function); confirmed on this project's PG17 instance. Note this count will **stay at 171** even after the fix — it queries the untouched `raw_source.fullText` audit copy, not `document_node`, so it's a discovery/scoping query, not a post-fix regression check. Use the corpus-wide backstop-suffixed count or a direct tree-shape spot-check instead to verify the fix's effect.

## Not yet automated

Every record above was found by ad-hoc SQL spot-checks (comparing `document.rawSource.fullText` length against total `document_node.text_content` length, then manually inspecting outliers) run by hand after each reindex pass — nothing in `server/src/law-index/` detects or records these automatically.
